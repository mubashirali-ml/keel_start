## Summary

Implements the ADR-0013 cap table rules: largest-remainder share allocation over exact
fractions (always exactly `total`, ties to the earlier founder), cumulative-floor monthly
vesting with a cliff (nothing lost or invented; `0/0` vests at month 0; cliff == vesting
vests at the cliff; dates via `add_months` from the incorporation date), `build_cap_table`
with friendly `FactsNotReadyError`s, and the CSV / Excel exports. `rules/cap_table.py`
does not import `rules.validation`; callers pass normalised facts.

### Decisions within the ticket (no new ADR needed)

- `build_cap_table` also raises `FactsNotReadyError` for an individual `equity_percent` outside `(0, 100]`
  and for negative or cliff-longer-than-vesting terms, so a caller that skipped validation gets a
  friendly error instead of negative shares or a `ValueError`. The pure functions
  `allocate_shares` / `vesting_schedule` raise `ValueError` on such inputs.
- "Fully vested on" = `add_months(vesting_start, vesting_months)` (the last event's date), ISO `YYYY-MM-DD` in CSV and a date cell in Excel.
- CSV "Equity %" shows at most two decimals without trailing zeros (`60`, `33.33`).
- "Vesting" sheet header: `Founder, Month, Date, Vested, Cumulative vested` (ADR-0013 lists these columns without fixing their captions).
- Workbook created/modified timestamps are fixed to the vesting start so the same cap table yields the same content.

### Round 1
Verdict: CHANGES_REQUESTED
Blocking:
1. launch_agents/rules/exports.py:76-84 and :100 — Founder names and emails (free text from the founder chat) go into `ws.append` / `vs.append` as plain strings, and openpyxl turns any string that starts with `=` into a formula cell. I checked this: a founder named `=1+2` comes back from `load_workbook` as `'=1+2'` with `data_type == 'f'`, so Excel shows a computed result instead of the name. That is spreadsheet formula injection in a file co-founders and team members download, and it also means the "Cap table" and "Vesting" sheets don't contain the founder's actual name. Done looks like: every text cell (Founder, Email in both sheets, plus the header and "Total" labels) is written as a literal string (for example, set `cell.data_type = "s"` after writing, or another way that keeps the value exactly as entered), and `tests/test_cap_table_exports.py` has a test where a founder's name and email start with `=` (and `+`, `-`, `@`), asserting the reloaded cells equal the literal text with `data_type == "s"` in both sheets.
Non-blocking:
- CSV has the same exposure (`=...` names in `cap_table_csv`) when opened in Excel. ADR-0013 fixes the CSV content, so neutralising it (for example with a leading `'`) is a Supervisor decision. Worth raising, but not required here.
- `rules/exports.py:38` `_percent` quantizes to 2 places, so unvalidated 3-decimal equity (33.335 / 66.665) shows as 33.34 / 66.66 in the CSV, which sums to 100 but no longer matches the shares (3,333,500 / 6,666,500). This is fine under the "callers validate first" contract; a docstring note would help.
- `build_cap_table` does not bound `vesting_months` (validation's `vesting_range` caps it at 120). A caller that skips validation with a very large term gets `ValueError: year 10000 is out of range` from `add_months` instead of a `FactsNotReadyError`.
- `_percent_text` (cap_table.py:29) and `_percent` (exports.py:38) are near-duplicates. Minor.
- The "Vesting" sheet identifies founders by name only, so two founders with the same name can't be told apart. Consider adding the email or founder id if T-021 or T-017 need it.
