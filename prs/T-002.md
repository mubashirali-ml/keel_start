## Summary

Implements `launch_agents/rules/validation.py`, the one deterministic module that tells the
Manager, the services and the UI whether the case facts are valid and complete:

- `apply_vesting_defaults(facts)` returns a deep copy with ADR-0013 defaults (48/12 when both
  are missing, cliff `min(12, vesting)` when only vesting is given, vesting 48 when only the
  cliff is given) and one founder-facing note per defaulted founder. The full default uses the
  exact ADR sentence; the two partial defaults get an equally friendly sentence saying which
  value was filled in.
- `missing_facts(facts)` returns the required keys still unknown in the ADR ask order
  (`business_description`, `entity_type`, `state`, `founders`, `incorporation_date`). Blank
  strings count as unknown; optional facts are never listed.
- `validate_facts(facts)` works on a normalised copy (state stripped and upper-cased, vesting
  defaults applied), reports every ADR-0013 issue code, and sets `ok` only when there are no
  issues and nothing is missing. The input is never mutated.

Every equity check is exact `Decimal` arithmetic (`sum == Decimal(100)`, precision via
`quantize(Decimal("0.01"))`), never float.

Small choices that the ADR leaves open (all inside this module):

- Issue `field` values: `founders` (`equity_total`), `founders.name` / `founders.email` /
  `founders.equity_percent` / `founders.vesting_months` / `founders.cliff_months` (per founder,
  always with `founder_id`), `state` (`invalid_state`, `entity_state_mismatch`).
- Issue order: per-founder issues in founder order, then `equity_total`, then state issues.
- One `vesting_range` issue per founder (the vesting one wins over a negative cliff), and no
  `cliff_exceeds_vesting` on top of a range issue, so the founder gets one clear message.
  A partial-default note is skipped when the value that was given is itself out of range
  (the issue explains it instead).
- `founder_email_invalid` also covers an empty email (founders added without one have `""`);
  the message then asks for an address. Duplicates are reported on the later founder and name
  the earlier one. Email syntax is a small regex (no network, no new dependency).
- `entity_state_mismatch` is reported only when a state is present (a missing state is
  already reported through `missing`).
- A founder without a name is called "Founder N" (from the id) in messages and notes.

Non-blocking:
- launch_agents/rules/validation.py:112 — when only the cliff is given and it is longer than 48 (e.g. 200), the note "I used the standard 48 months with the 200-month cliff you gave" is emitted alongside `cliff_exceeds_vesting`. That is harmless because `ok` is False and the issue explains it, but the note could be skipped when `cliff > DEFAULT_VESTING_MONTHS`, the same way out-of-range values already skip it.
- launch_agents/rules/validation.py:222 — when both vesting and cliff are negative, only the vesting `vesting_range` is reported. The founder sees the cliff problem only after fixing vesting. This is acceptable under ADR-0013 ("one clear message") and is documented in the PR.
- The partial-default notes use their own sentences instead of the ADR-0013 template. That is the right call, since the template's "48 months with a 12-month cliff" would be false for a partial default. A future ADR revision could make these sentences binding as well.
- `_FOUNDER_NUMBER` duplicates `domain.types._FOUNDER_ID`. This is minor and fine because `rules` should not import private domain helpers.
