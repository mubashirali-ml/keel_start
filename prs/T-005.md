## Summary

This PR implements the T-001 stubs in `persistence/engine.py` and `persistence/repository.py`.

- **Engine.** `create_db_engine(url)` supports SQLite and PostgreSQL only. On SQLite it sets
  `check_same_thread=False`, runs `PRAGMA foreign_keys=ON` on every connection, and uses
  `StaticPool` for `sqlite://`. On PostgreSQL it uses `pool_pre_ping=True` and passes
  `options=-c statement_timeout=15000`. `postgresql://`, `postgres://` and
  `postgresql+psycopg2://` URLs become `postgresql+psycopg://`. Any other URL raises `ValueError`.
- **Migrations.** `init_db(engine)` runs Alembic `upgrade head` in code. It loads the repo's
  `alembic.ini` and passes the connection through `config.attributes`. It never changes the
  app's logging. `schema_is_current(engine)` compares the database heads with the script heads.
  It returns False for an empty database, for one behind head, and for one it cannot reach.
- **Repository.** Built on SQLAlchemy Core over the T-001 tables. Only pydantic objects come out.
  Each method runs in its own transaction. `transaction()` binds this same repository to one
  connection for the current thread or task through a per-instance `ContextVar`. Inside the block
  the yielded object and `repo` are the same object. Nested blocks join the outer one, and other
  threads are not affected.
- **Behaviour choices inside the ADR contract:**
  - Unknown case, document, build or user ids raise `NotFoundError`, including `list_*` on an
    unknown case. The one exception is `list_cases`, which returns whichever of the given ids
    exist.
  - `append_messages` first runs a no-op `UPDATE` on the case row. This takes a row lock on
    PostgreSQL and the write lock on SQLite, so concurrent appends keep `seq` without gaps. It
    always assigns `id`, `case_id` and `seq`. It keeps a `created_at` the caller already set
    (useful for seeded history) and stamps "now" otherwise.
  - `save_document` makes the optimistic check twice: once by reading the stored version, then
    again with `UPDATE ... WHERE version = expected_version`. A save without `expected_version`
    on a document that already exists raises `StaleVersionError`.
  - A second document with the same (case, kind, founder) raises `ConflictError`, company-wide
    documents (`founder_id = None`) included. `save_document` takes the case lock first and then
    checks explicitly, because the UNIQUE constraint treats NULL founder ids as distinct. A site
    build whose (case, version) already exists also raises `ConflictError`. A caught
    `ConflictError` leaves an enclosing `transaction()` usable on both databases: on PostgreSQL
    the constraint-prone statement runs in a savepoint.
  - A document or build never moves to another company: an update whose `case_id` differs from
    the stored row raises `NotFoundError`.
  - Every signature in `doc.signatures` must be for `doc.version`, and a founder signs a version
    at most once; otherwise `ValueError`. Older signature rows stay for history.
  - `list_documents` sorts by `DocumentKind` declaration order, then by founder order in the case
    facts. Founder-less documents come first within a kind. Signatures come back in signing order
    (`signed_at`, then `founder_id`).

## Builder response

### Round 1

1. **Fixed: a caught `ConflictError` aborted the PostgreSQL transaction.** The insert and
   update in `save_document`, and the insert/update in `save_site_build`, now run inside
   `Repository._savepoint(conn)`. On PostgreSQL that is `conn.begin_nested()`, so only the
   savepoint is rolled back and the enclosing `transaction()` stays usable. On SQLite it
   deliberately does nothing. SQLite already rolls back only the failing statement. A real
   savepoint there would be harmful: pysqlite's legacy transaction mode sends no `BEGIN` before
   the first write, so `RELEASE SAVEPOINT` commits the enclosing transaction early. I
   reproduced that: a `begin_nested()` insert inside `engine.begin()` survived the outer
   rollback. Using the savepoint on PostgreSQL only gives the same observable behaviour on
   both databases, which is what ADR-0027 asks for. New test
   `test_a_caught_conflict_inside_a_transaction_leaves_it_usable`, run on both databases
   through `db_engine`. Inside `repo.transaction()` it catches `ConflictError` from a
   duplicate site build version (insert and update, both via the database constraint), a
   duplicate founder document and a duplicate company-wide document. It then writes a
   checklist tick, a message and another build, and checks that all of them committed. Also
   new: `save_document` rejects two signatures by one founder for the same version with
   `ValueError` up front, rather than with a raw `IntegrityError` on the signatures primary key.
2. **Fixed: duplicate company-wide documents were accepted.** `save_document` now takes
   `_lock_case` first. Under that lock it checks for another document with the same case and
   kind, and the same founder (`founder_id IS NULL` for company-wide documents). If one exists
   it raises `ConflictError`. The check runs on updates too, so an update cannot turn one
   document into a twin of another. The schema is unchanged. `test_save_document_rules` now
   covers the founder-less duplicate, both update-into-twin cases, and the same kind in
   another company (allowed). `test_concurrent_company_wide_inserts_store_exactly_one` starts
   4 threads behind a barrier: one save succeeds, three get `ConflictError`, and one document
   is stored, on both databases.

Non-blocking items, also handled:
- `make_signature` and the feature run now use `ESIGN_CONSENT_VERSION`.
- The update paths of `save_document` and `save_site_build` compare the stored `case_id`. On a
  mismatch they raise `NotFoundError` instead of moving the row (tested).
- Because `save_document` now takes the case write lock before its first read, concurrent saves
  of one document on SQLite wait for each other and give `StaleVersionError`, not
  `database is locked`. Tested by `test_concurrent_saves_of_one_version_give_one_winner_and_stale_errors`
  (4 threads, on both databases: one is saved, three get `StaleVersionError`).
- Caller-supplied `created_at` in `append_messages`: kept as documented (seeded history). Not changed.

### Round 1
Verdict: CHANGES_REQUESTED

Checked: `bash scripts/verify.sh T-005` -> PASS (622 passed, 24 skipped). The Reviewer also ran a
throwaway local PostgreSQL 18 cluster. With `LAUNCH_TEST_POSTGRES_URL` set, `tests/test_persistence.py` and
`tests/test_migrations.py` all pass on PostgreSQL, the concurrent-append test included, and so does the
PostgreSQL part of `evidence/T-005/feature_run.py`. The engine options, migrations, round trips, evidence
fields, cascade, `transaction()` and the feature run meet the acceptance criteria. Scope is clean and there
are no new dependencies. Two defects remain.

Blocking:
1. `launch_agents/persistence/repository.py:422-430` (`save_document` insert) and `:609-618` (`save_site_build`) —
   On PostgreSQL, a caught `IntegrityError` aborts the whole transaction. These two methods turn that error into
   `ConflictError` and let it propagate. Outside `transaction()` this is harmless. Inside `repo.transaction()`
   on PostgreSQL, though, the shared connection is left in a failed state. A caller that handles the
   `ConflictError` and continues then gets a raw `psycopg.errors.InFailedSqlTransaction` ("current transaction
   is aborted") on its next call. On SQLite the same code works. Reproduced: inside `transaction()`, save a
   duplicate document, catch the `ConflictError`, then call `set_checklist_item`. SQLite: OK. PostgreSQL:
   `InternalError`. This is the kind of dev/prod split that ADR-0027 ("work on SQLite and PostgreSQL") rules
   out, and the SQLite test suite cannot catch it. — Done looks like: run each insert or update that can raise
   `IntegrityError` inside a savepoint (`conn.begin_nested()`), so a `ConflictError` leaves the surrounding
   transaction usable on both databases. Add a test, run on both databases through the `db_engine` fixture:
   inside `repo.transaction()`, catch the `ConflictError` from a duplicate document and from a duplicate site
   build version, then make further writes that commit.
2. `launch_agents/persistence/repository.py:420-430` — `save_document` does not enforce "one document per
   (case, kind, founder)" for company-wide documents (`founder_id = None`). The UNIQUE (case_id, kind,
   founder_id) constraint treats NULLs as distinct on both SQLite and PostgreSQL. So a second
   `OPERATING_AGREEMENT_SUMMARY` with `founder_id=None` and a new id is accepted, and `list_documents` then
   returns two. Reproduced on both databases. The PR record says such a save raises `ConflictError`, but the
   test (`test_save_document_rules`) only covers `founder_id="f1"`. A double submit of "generate documents"
   would produce two operating agreements to sign. — Done looks like: on insert, check for an existing document
   with the same case, kind and founder (with `founder_id IS NULL` for company-wide documents). Do this
   while holding the case lock (`_lock_case`) so two concurrent inserts cannot both pass, and raise
   `ConflictError`. Extend `test_save_document_rules` with the founder-less case. The schema stays as T-001
   made it.

Non-blocking:
- `evidence/T-005/feature_run.py:118` and the test helper `make_signature` use `consent_version="esign-2026-11"`
  instead of `ESIGN_CONSENT_VERSION` ("2026-11-23"). Using the constant would make the evidence realistic.
- `save_document` (update path) and `save_site_build` (update path) never compare `doc.case_id` /
  `build.case_id` with the stored row. `save_site_build` can even move a build to another company. A guard
  that raises `NotFoundError` or `ValueError` on a mismatch would be safer.
- On SQLite, `save_document` reads before it writes, inside a deferred transaction. Two concurrent saves of the
  same document can therefore fail with `OperationalError: database is locked` instead of
  `StaleVersionError`. This happens in development only: PostgreSQL behaves correctly, because of the
  `UPDATE ... WHERE version = ...` check.
- `append_messages` keeps a caller-supplied `created_at`. ADR-0012 says that the repository assigns it. The
  choice is documented and is useful for seeding, but callers should know about it.
