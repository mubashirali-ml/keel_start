## Summary

Implements the pure sign-off state machine in `launch_agents/signoff/machine.py`:
`create_document`, `sign`, `edit`, `regenerate` and `is_legal_complete`, with the exact
ADR-0014 rule order and the ADR-0031 changes. Every signature is built from the
`SignatureEvidence` it was given and is accepted only when `evidence.content_sha256`
equals `document_sha256` of the content being signed (the current content for `sign`,
the new content for `edit`). Every action, rejections included, returns its audit
entries in `SignOffOutcome.audit`. Functions take an injected `now`, do no I/O and never
mutate their inputs: they build new `Document`s, and rejections return the input document as it was.

## Behaviour details (choices inside the ADRs)

- **Rule order** (ADR-0014): stale first (version, then content hash, ADR-0031), then not-a-signer, then already-signed (`sign`), or unchanged content (`edit`). So a stale request from a non-signer is reported as stale.
- **Audit entries.** `actor` is the founder id for `sign`/`edit` and their rejections, `"system"` for `create_document` and the `actor` argument for `regenerate`. `SIGNED` and `EDITED` detail is exactly `{"user_id", "typed_name", "content_sha256", "ip"}` (ADR-0031). `SIGNATURES_INVALIDATED` detail is `{"founders": [...]}` (ADR-0014). `REJECTED_*` detail carries `operation` (`sign`/`edit`) and the reason (`version` or `content_sha256` for stale). `EXECUTED` detail is `{"signers": [...]}`. `from_version`/`to_version` are set on every entry.
- **Entry order on edit:** `REOPENED` (only if it was executed), `SIGNATURES_INVALIDATED` (only if someone else's signature was cancelled; no empty entry), `EDITED`, then `EXECUTED` (only when the editor is the sole required signer, e.g. an 83(b)). The edit records only the `EDITED` entry for the editor's new signature, not a separate `SIGNED` entry, following ADR-0014's list.
- **Unchanged content** for `edit`/`regenerate` is compared by `document_sha256`, so a change that only touches line endings (`\r\n` vs `\n`) counts as no change: it is a no-op, with no new version and no cancelled signatures.
- **StaleVersionError messages:** a wrong version gives the ADR-0014 text ("This document changed to version {n} while you were looking at it. Review the new version first."). A hash mismatch gives "This document changed while you were reviewing it. Review version {n} and sign again." (the ADR-0031 opening). `details` has `current_version` in both cases.
- **`regenerate`** replaces content, title and required signers from the draft, cancels all signatures (`invalidated` lists them, and so does the `REGENERATED` detail as `founders`) and records `content_sha256`. A draft for a different document (other `kind` or `founder_id`) raises `ValueError`. That is a caller bug, not a founder-facing rejection.
- Document ids come from `new_id("doc")`.

Non-blocking:
- `launch_agents/signoff/machine.py:137`: the hash check is an exact string compare, so an uppercase-hex `content_sha256` from a client would be rejected as stale. T-015 should normalise (or the API should require lowercase hex) when it builds `SignatureEvidence`.
- `launch_agents/signoff/machine.py:104`: `_all_signed` ignores `Signature.version` and relies on the invariant that `signatures` holds only current-version entries. That holds for every path in this module. A persisted document loaded with old-version signatures (T-015/T-012 bug) would be treated as signed, so a version filter here would be cheap extra protection.
- `launch_agents/signoff/machine.py:270`: `regenerate` raising `ValueError` for a draft of another kind or founder goes beyond ADR-0014. It is reasonable and documented in the PR, but T-015 must match drafts to documents by (`kind`, `founder_id`) before calling it.
- `tests/test_signoff.py`: no test covers an edit whose evidence hash is wrong on an already executed document, or a stale-hash edit by a non-signer (stale should win). The behaviour follows from `_check_stale` running first, so this is coverage only.

Checked: all 9 acceptance criteria against code and tests; ADR-0014 rule order (stale, then not-signer, then already-signed or unchanged); ADR-0031 evidence binding (`sign` checks the current content, `edit` checks the new content, and the editor's signature on the new version carries its own evidence); audit on every rejection; no input mutation (deep copies, rejections return the input as it was); scope (only owned paths changed, no new dependencies); `bash scripts/verify.sh T-004` -> PASS; `evidence/T-004/run.log` walks the exact ticket scenario with asserted checks (10-entry trail, both stale variants, execution, regenerate reopen).
